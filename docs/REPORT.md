## 1c. Demonstration dataset rebuilt from the uploaded documents

Prompt 4 asked for the Phase 1 pack to be the demonstration data, analysed by the app rather than
transcribed into it. That is what now sits in the demo session.

### How it is produced

`node scripts/build-demo-dataset.mjs` runs offline and does **not** contain any CSSS finding:

1. reads `demo/manifest.json` (session objective, target cycle `AY 2026–27`, two source entries);
2. hashes each upload with SHA-256 and refuses a duplicate — `FAQ_DOHE_CSSS.pdf` and
   `FAQ College And University Students.pdf` are the same bytes, so the second would be skipped, not
   counted as corroboration;
3. extracts every page with the project's own extractor (`scripts/extract_pdf.py` →
   `api/extract.py::_extract_pdf`, PyMuPDF) and records page numbers;
4. chunks page-preservingly with the shipped `chunkPages`;
5. takes requirement titles from `demo/inventory/evidence_claim_requirement_map.csv` — **only** the
   requirement id and title columns; the file's `relation`, `claim_paraphrase` and
   `verification_status` columns are never read, so no expected answer can leak in;
6. scores every chunk against every requirement with the shipped IDF-weighted scorer, keeps the
   best-matching sentence as the excerpt, and derives each relation;
7. runs the shipped cycle examiner, which compares the academic years a passage mentions with the
   target cycle;
8. derives requirement status with the shipped rule, then findings and the checklist;
9. writes `supabase/seed/csss_source_driven.sql` and `demo/build-summary.json` (regenerate, never
   hand-edit).

The TypeScript builders are loaded through `scripts/lib/load-shipped.mjs`, which slices the shipped
files and strips types with esbuild — so the pipeline calls the same functions the Edge Function
does, not a copy that can drift.

### What it produced (executed)

| Stage | Result |
|---|---|
| Sources | 2 uploaded PDFs, both `extracted`, `extractor=pymupdf`; 7 pages / 10,225 chars and 8 pages / 19,633 chars |
| Chunks | 15, one per page, every excerpt traceable to a page |
| Requirements | 13 (researcher titles), 8 categorised `figures`/`process`/`eligibility`/`documents`/`continuation`/`timing` |
| Excerpts → requirements | 12 excerpts, 30 links |
| Requirement status | 5 found, 6 partial, 1 not found, 1 outdated |
| Findings | 2: `gap` (No other scholarship — none of the reviewed excerpts settles it) and `outdated` (Scheme valid for 2026-27 — the passages reviewed describe earlier cycles) |
| Checklist | 8 items, covering both findings and the requirements that are only partly supported |

Two behaviours worth pointing at, because they are the ones that were wrong before this round:

- **"Application deadline for 2026-27" is `partial`, not `found`.** Neither PDF contains a calendar
  deadline for 2026-27; the only deadline language is "renewal deadline" and "closing date of NSP",
  and the cycles quoted are 2008-09 … 2025-26. The analyzer says so instead of inventing a date.
- **"Scheme valid for 2026-27" is `outdated`.** Every passage that could have supported it refers to
  an earlier academic year, so support was downgraded with the reason recorded per link: *"This
  passage refers to 2022–23, not to the target cycle starting 2026."*

Both PDFs are undated on their face; the dates recorded come from PDF metadata, and the report of
each source states that basis. The guidelines PDF is a 2018 paper capture whose text layer is OCR
output ("80111 percentile", "Income Cenificate"), which is recorded in that source's notes — the
figure should be read off the page image before it is relied on.

### Provenance categories in the interface

Every source, excerpt and finding carries a numbered category, and the session page shows the key:

| # | Category | How it is decided |
|---|---|---|
| 1 | Uploaded demonstration source | anything the researcher supplied (uploaded PDF, runtime upload, note). Never described as live-verified. |
| 2 | Live retrieved source | only a source fetched from its own URL in this session |
| 3 | AI-generated potential finding | only a finding whose `engine` is `gemini` |
| 4 | Requires independent verification | rule-based findings and flagged checklist items |

An uploaded official document therefore cannot be rendered as "currently live-verified": it is
category 1, and the source note says the file was not re-fetched.

## 4. Known limitations

1. Without `GEMINI_API_KEY`, requirement decomposition uses an 8-question structural template and
   evidence mapping uses lexical scoring. Both are labelled `heuristic` in the UI and in the job row.
2. The demo dataset is **not** live-retrieved: the two PDFs were supplied in the Phase 1 pack and
   were not re-fetched from the web. The session is shown with the disclaimer *"Demonstration
   dataset built from the two documents supplied in the Phase 1 pack … verify against the current
   official NSP portal before making application decisions"*, and both sources are category 1
   (uploaded) on the provenance key — never "live-verified".
3. Sources recorded from the inventory without a URL show **"URL unavailable for verification"**
   instead of a fabricated link; the snippet-only scheme page is marked `quote_verified = false`.
4. Sessions with no owner are readable with the anon key (required for a no-login demo). Enabling
   Auth and setting `owner_id` scopes them with no schema change.
5. Password reset email is limited by Supabase's default SMTP.
6. The deployed `extract-source` and `analyse` both predate this round's fixes (see §1
   “Blocked by configuration”) — redeploy to sync live runs. The demonstration dataset is
   unaffected: it was produced by the current code.
7. **Concurrent analysis runs are not locked server-side.** The client refuses a second run in the
   same tab, but two tabs pointed at the same session could each invoke `analyse`; the evidence
   stage deletes and re-inserts a source's evidence, so the outcome is duplicated or partially
   rewritten rows, recoverable by re-running. A guard belongs in the function (refuse if a
   `running` job for the same session+stage is younger than ~2 minutes) and requires an Edge
   Function redeploy, which cannot be verified from this sandbox — so it is documented rather than
   shipped untested.
8. The lexical scorer is deliberately strict. It requires a passage to contain essentially all of a
   requirement's own terms before it will say "found", and it downgrades support from a passage
   about an earlier academic year. The cost is false negatives: a document that paraphrases heavily
   will be marked partial. That is the intended trade — a missed finding is recoverable, a false
   "found" is not — but it is a trade, not accuracy.
9. The coverage figure is importance-weighted evidence coverage of the reviewed sources, with the
   formula and weights shown; it is never presented as a completeness percentage of reality.

## 5. Three-to-five minute demonstration

1. **Landing (20 s).** Headline: *"The most important information might be the information you
   haven't found."*
2. **Open the demonstration case (30 s).** `/app/history` → *Demonstration*. Read the amber banner:
   the dataset came from the two supplied PDFs, the text was extracted here, no model was called.
   Underneath it, the provenance key — four numbered categories, so an uploaded document is never
   read as live-verified.
3. **Sources tab (40 s).** Two sources, both category 1 (uploaded), 7 and 8 pages, `pymupdf`, with
   the original filename, the SHA-256, the date basis and the OCR caveat printed under each. One
   file has a recorded URL, the other does not — and says so instead of showing a fabricated link.
   **Extracted text** opens the stored page text the analysis ran on, page by page.
4. **Overview (40 s).** Coverage chart with its formula in the tooltip. Line: *coverage is coverage
   of the sources reviewed, not of reality.* Status mix: 5 found, 6 partial, 1 not found, 1 outdated.
5. **R09 — deadline for 2026-27, partial (45 s).** Open it. The excerpt is real page text; the
   relation is PARTIAL with the reason, and the session's target cycle is 2026-27 while the passages
   quoted run to 2025-26. Nothing here invents a date.
6. **R13 — outdated (40 s).** Every passage that could have supported "the scheme is valid for
   2026-27" refers to an earlier academic year, so support was downgraded per link with the reason
   recorded. Explain the rule: undated is never called outdated; an earlier cycle is.
7. **R04 — not found (30 s).** "None of the excerpts reviewed addresses this requirement" plus the
   sentence that this is *not* evidence it does not exist.
8. **Evidence drawer (40 s).** Click an excerpt: category badge, source, issuer, date, page, the
   exact excerpt, how it was matched, and **Open at page N** — which opens the uploaded PDF at that
   page, from the copy the app serves.
9. **Checklist (25 s).** 8 items, prioritised, each naming the authority to ask. Tick one; the count
   moves and persists.
10. **Live run (30 s, if the functions are redeployed).** New research → upload a PDF or paste a URL
    → Run analysis. Say which engine ran; with no `GEMINI_API_KEY`, the heuristic label is shown
    rather than an AI claim.
11. **Close.** "We don't answer your question. We tell you what your evidence does not establish, and
    what to verify next."
